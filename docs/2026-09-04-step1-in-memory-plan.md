## 1. 工作项

编号供批注引用。工期是净开发时间，不含等人工导出 RVM 的时间。

### W1 · 拆 D3 的账（半天，零几何）

`catalog_pending` 一本拆两本：
- `catalog_pending` —— 只留「E3D 也不画 / 无 GMRE / 表现过滤掉」的记账；
- `not_wired` —— 「有明确建模路径、只是还没接线」，即 SCTN / GENSEC / FITT / FIXING / PFIT / STWALL 那 1 万件。

`totals_line` 带上 `not_wired`。**之后每次复跑，第一步的进度就是这一个数。**

- 改动面：`pipeline.rs`（Report 字段 + merge + totals_line）、`category.rs`（判据来源）。
- 验收：五库复跑，`not_wired + catalog_pending` 之和等于改动前的 `catalog_pending`；`accounts_for` 不破；`cargo test` 全绿。
- 风险：低。不动几何、不动键。

### W2 · 补 D2 的 5 个 noun（半天）

DDAT / DDSE / DPSE / LNKI / LNKS → `NonGraphic`（`data/noun-family-matrix.json` 里三项皆空、`gb = 0`，recheck-2 §2.7）。加 `noun_coverage` 断言钉住，防回潮。

- 验收：ams7997 `unknown_nouns` 空；`proven_non_graphic` 多出这 5 行。
- 风险：低。若这 5 个里有任何一个其实带几何，账上会以「该出没出」暴露——所以要断言，不要只改表。

### W3 · 表示探针：`-ref` 第二遍到底是不是目录 OBST（半天）

`ELMODL` 对管件/吊架会跑第二遍，产出 `-ref` 段（绝热·障碍，透明度 12/25/50/75/87）。我们已实现的是**目录图元侧**的 `OBST/TUFL/CLFL` 门。两者是不是同一件事，静态看不出来。

- 做法：取一只带绝热的管件，`REPRE INSU ON` / `OFF` 各导一次 TTY，比对图元数；同时活桥看 `GTGEOM` 在透明度非 0 时走的是不是同一条目录路。
- 为什么排在接线之前：**结论可能改 `GeometryId` 的形状**，键一旦发出去就改不动。
- 两种结局：是同一件事 → 现状不欠，只在总纲写死；不是 → 模型集少一整类，且账面看不出来，得单开一本。

### W4 · 按件数接线（主体工作量）

每接一条，`not_wired` 少一批。施工图全在 recheck-2 §2、§3，本文不重复。

| 序 | 项 | 件数 | 依赖 | 工期 |
|---|---|---:|---|---|
| W4-1 | SCTN 直段（接线 → 两端切面 → 负体） | 2330 | 截面求值 ✅；负体等 W4-2 | 2 天 |
| W4-2 | FITT / PFIT / CMFI / FIXING（目录路复用，新活只有标架） | 3432 | `GFIORI` / `GPFORI` / `GCORG3` 反编译；G2-5 收口排前面 | 2 天 |
| W4-3 | GENSEC 扫掠 | 4203 | 截面求值 | 2 天 |
| W4-4 | STWALL（放置来源未定，先定性） | 302 | `element_probe` 取 3 只 | 1 天 |

- 每条的验收都一样：该库 `not_wired` 对应行归零或只剩点名的例外；RVM 局部系逐件对拍新增几何 100% 配对；**其它 noun 的 `model.obj` 逐字节不变**。
- 顺序理由：SCTN 有现成 RVM 参考（S4001 / L40X4 / HW150 / C80），先拿它把端切口径钉死；FITT 族件数第二且能直接复用目录路；GENSEC 件数最大但没有参考样本，排第三。

### W5 · D4 的 `host_negatives`（1559 件，1.5 天）

`TMPL` 底下的负体扣的不是容器自己，是容器之外的宿主（消防水带箱的 `NXTR` 是墙上凹龛，端板的 `NBOX` 是梁廓开口）。这条机制整条没有。排在结构线之后——它改的是「谁扣谁」，接线期间动它会把两库对拍搅浑。

### W6 · 分段计时（半天，不改行为）

`gen_ams` 现在只有一个总时长。加六档：**读库 / 分类 / 建体 / CSG 布尔 / 三角化 / 记账**，五库各跑一遍出热点表。

**这一项不是优化，是优化的前置**。放在这里是因为它零风险且能顺手做；真正动性能等 W4 接完。

### W7 · 两处结构性错配（**不在第一步出口条件里，列出供拍板**）

- **W7-1 变换方向反了**：core.dll 是自顶向下累乘（`SGDRAW` 的 `MAT16`/`CONCAT` → `GLSMAT`）；我们 `transform.rs:79 world_matrix` 自底向上逐元素重走 owner 链，而 `DbSet::element()` 每次造新句柄、`parsed` 是空 `OnceLock`，于是每个祖先被反复 `search_index` + 解析。量级 O(n·d)（**结构推算，未实测**）。
  - 便宜修法：`DbSet` 加 `(dbno, refno) → Arc<ParsedElement>` 共享缓存，零行为变化。
  - 结构正确修法：DFS 把父的世界矩阵带下来，`model_element` 收 `parent_world`。改 API。
- **W7-2 没有「意向」这一层**：core.dll 用 `SETWNT`/`BXWANT`/`SLWANT` 让调用方先声明要盒还是要实体（`cachegml/GTCLSH@0x10340300` 实证）。我们不管谁调都建完整 CSG + 三角化。房间、碰撞、体积统计只要盒。
  - 它**影响 `generate()` 的签名**，所以要么现在预留 `Want` 入参，要么明确以后再开一条平行链。

## 3. 贯穿约束（每一步都过）

1. `accounts_for` 硬判据不破。
2. `cargo test` 全绿，且**不许为了变绿放宽断言**。
3. 触碰复用池 / 求值器的改动，两库 `model.obj` / `elements.json` 逐字节一致，或逐件归因。
4. 只读库身份（DB SHA-256）前后一致。
5. 新补的每条臂**先贴 Core3D / core.dll 反编译锚点，再写代码**。
6. 判据只许写一份，全量与增量共用同一个函数（`is_model_unit` 与短 `DESP` 那两次都是同一个形状的事故）。

---

## 4. 明确不做（这一步的边界）

- 不做持久化格式变更、不动增量管线。
- 不做性能优化（W6 只是量，W7 只是列出来拍板）。
- 不做几何精度调优（弦容差、分段数）——那属于对拍阶段。
- 不碰 `GeometryId` 的形状，**除非 W3 的结论要求**。
